# 12. Архитектурная основа: модель проекта

Черновик для обсуждения. Вырос из разбора старого объекта (`11-legacy-analysis.md`) и из того,
как прототип развалился на типовом объекте (`08-navigation.md`).

## Правила

1. **Каждая сущность существует один раз.** Помещение, устройство, тип, зона — запись с постоянным
   `id`. Все ссылаются на неё по `id`, а схема проверяет ссылки при сохранении. Опечатка или
   коллизия имён не может пройти.
2. **Имя для людей отдельно от идентификатора.** `id: bed1`, `name: «Спальня»`,
   `code: «L6»` по электропроекту, `aliases` для поиска.
3. **Новое устройство = одна запись + привязка в драйвере.** Код интерфейса при этом не меняется.
4. **Логика и производные состояния — в ядре.** Клиент только показывает и отправляет команды.
5. **Один клиент — много видов.** Телефон, планшет, стенная панель и сервисная панель читают одну
   модель. Навигация «где» и «что» выводится из модели, а не пишется руками.
6. **Тема не трогает структуру.** Тренды — токены, скины контролов и флаги, без копий экранов.
7. **Выключить функцию можно конфигурацией:** флаги `hidden`, `disabled`, `serviceOnly`
   с причиной. Без переименований вроде «(не работают)».

## Слои

```
Проект объекта (данные, git, схема)
  ├─ Пространство: участок → этажи → помещения → зоны
  ├─ Каталог типов устройств (общий для всех объектов)
  ├─ Экземпляры устройств + привязки к шинам
  ├─ Подсистемы: медиа-граф, климатические контуры, разделы охраны
  ├─ Сцены и экземпляры поведений
  └─ Представление: избранное, порядок, фото и хотспоты, план, тренд
        │
Ядро: состояние, производные, поведения, журнал, API
        │  snapshot (модель + состояние), дельты, команды по id устройства
Драйверы: адреса шины ⇄ свойства типа   ← единственное место, где живут joins, группы KNX, регистры Modbus
        │
Клиенты: приложение (телефон / планшет / панель), сервисная панель
```

## Сущности

### Пространство

```yaml
site: { id: sosny, name: «Дом в Соснах» }
floors:
  - { id: f0, name: Подвал, level: 0 }
  - { id: f1, name: 1 этаж, level: 1 }
spaces:                       # помещения по проекту, как на планах
  - { id: hall1, floor: f1, name: Холл, code: L2, kind: hall }
  - { id: living, floor: f1, name: Гостиная, code: L3, kind: living }
  - { id: bath3, floor: f3, name: Ванная, code: L13, kind: bath }
zones:                        # то, как дом видит пользователь; могут пересекать помещения
  - { id: living-zone, name: Гостиная, spaces: [living], extra: [hall1.pillars, hall1.spot] }
  - { id: baths, name: Ванные, spaces: [bath1, bath2a, bath2b, bath3], kind: group }
```

- **Помещение** — физическое место по проекту.
- **Зона** — то, что видит жилец: открытая планировка, «все ванные», «второй этаж».

Устройство числится в одном помещении, но может показываться в нескольких зонах. Это ответ на
случай `L2-4/1`, который в проекте числится в холле, а живёт в гостиной.

### Тип устройства (каталог)

```yaml
id: light.dimmer
traits: [onoff, level]
commands: { toggle: {}, set: { level: 0..100 } }
ui: { icon: bulb, widget: dimmer, longPress: levelSheet }
```

Ещё примеры: `shade.motor`, `tv.ir`, `climate.regulator`, `climate.ac`, `sensor.occupancy`,
`security.sensor`.

- Тип описывается один раз на все объекты.
- Пульт Samsung — это ИК-профиль типа `tv.ir`, а не 45 кнопок на комнату.

### Устройство (экземпляр)

```yaml
id: bed1.luster
type: light.dimmer
space: bed1
name: Люстра
role: main            # main | accent | mood | sconce | outlet … — для сцен и сортировки
order: 1
bind: { driver: knx, ga: { onoff: 1/6/1, level: 1/6/2, status: 1/6/3 } }
flags: {}             # hidden / disabled / serviceOnly + reason
```

### Подсистемы

- **Медиа:** граф узлов и портов (источники, матрица, ресиверы, экраны, зоны мультирума),
  аренда источников, сессии комнат (`05-media.md`).
- **Климат:** контуры помещения — пол, радиатор, кондиционер, вентиляция — с отдельными
  уставками, плюс координатор дома (`06-climate.md`).
- **Охрана:** разделы, датчики со ссылкой на помещение, камеры со ссылкой на помещение
  или участок.

### Представление

Отделено от модели, чтобы дизайн объекта не ломал структуру:
- избранное и порядок для каждого пользователя;
- фото помещений и хотспоты;
- геометрия плана;
- тренд, профили клиентов, стенная панель → своё помещение.

## API ядра для клиентов

- **`model`:** пространство, типы, устройства, подсистемы, представление. Приходит при
  подключении и при горячей перезагрузке.
- **`state`:** snapshot, затем дельты `{ device, trait, value }`. Производные состояния ядро
  отдаёт как обычные: `space.living.lightsOn`, `ventilation.on`, `media.session.living`.
- **`command`:** `{ device, command, args }` или `{ scene }`.
- Клиент не знает, Crestron там, KNX или Modbus.

## Проверка основы

Первым настоящим объектом модели будет **старый дом из разбора** (`11-legacy-analysis.md`).
Переносим его из SIMPL и iRidium в новую модель целиком: около 20 помещений, 74 светильника,
16 штор, 29 климатических контуров, 9 медиа-зон, 67 датчиков охраны.

Критерии:
- клиент показывает весь дом без единой строки, написанной под этот объект;
- новый светильник — одна запись;
- телефон и планшет — один код;
- тёмная тема — без копий экранов.
