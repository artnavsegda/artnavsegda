# 11. Разбор старого объекта: почему проекты разваливались при масштабе

Источник: реальный объект автора, сделанный около 2019–2020 года.
- Логика — две программы SIMPL Windows: `ap3.smw` (свет, шторы, климат) и `cp3.smw` (медиа, охрана).
- Интерфейс — два проекта iRidium: `phone_server.irpz` и `tablet.irpz`.
- Сами файлы лежат в GitLab автора, в этот репозиторий не копировались.

## Объект в цифрах

| | |
|---|---|
| Этажи | подвал (гараж, котельная, техпомещение, коридор) + 3 этажа |
| Помещения | около 20, в том числе 4 ванные, 3 холла, лестница, балкон |
| Свет | 74 нагрузки, 13 клавишных панелей, 11 датчиков присутствия |
| Шторы | 16 моторов, включая экран проектора |
| Климат | 29 контуров: тёплый пол и радиатор почти в каждой комнате, у каждого свой регулятор по KNX. Кондиционеры через CoolMaster в 4 комнатах, приточные установки (Lessar, Segnetics), вытяжки в ванных. |
| Медиа | 4 ТВ Samsung по ИК, матрица WyreStorm, 2 Apple TV, Kodi, 2 ресивера Yamaha, проектор JVC с лифтом и экраном, усилитель на 6 зон, зоны в ванных всех этажей |
| Охрана | Jablotron, 67 датчиков, 4 раздела, ворота, шлагбаум |
| Сцены | 10 на весь дом |
| Протокол к интерфейсу | 750 joins у AP3 и 560 у CP3; у iRidium Server 884 канала |

## Что ломало масштаб

1. **Нет единого реестра помещений.**
   - Гостиная записана пятью способами: `Living_room`, `Livingroom`, `Living Room`, `L3 Living room`, `3 Living room`.
   - Опечатки: `Kids_toom`, `3nd_Floor`, `Kitechen`.
   - Коллизии: `Hall` — три разных холла, `Bathroom` — ванные 1-го и 3-го этажей.
   - Три нумерации: электрика L1–L15, климат 1–14, зоны усилителя Room1–8.
2. **Электрическое помещение ≠ пользовательская комната.** Контуры `L2-3` и `L2-4/1` по электропроекту относятся к холлу, но пользователь видит их в гостиной (открытая планировка). Нагрузки `L14` одновременно в `Workshop` и `1st_level`.
3. **Карта joins — база данных, которую ведут руками.**
   - Свет разложен по функциям с шагом 100: вкл / выкл / переключить / сохранить, плюс уровень.
   - Новый светильник = свободный индекс в пяти диапазонах сразу.
4. **Копирование вместо типов.**
   - Модуль диммера повторён 51 раз, регулятор температуры — 22.
   - Пульт Samsung на 45 кнопок — на каждую из 4 комнат, и ещё дважды: обычный и `[MOS]`.
5. **Модель дома жила в коде интерфейса.**
   - Больше 30 файлов «комната × функция» на телефоне.
   - В каждом — русское имя, иконка и строка сигнала, заданные руками.
   - Планшет держал свою копию.
6. **Два клиента — два проекта и две навигации.** Телефон: сначала функция → комната. Планшет: сначала этаж → комната. Каждое изменение — дважды.
7. **Темы копированием.** `Floor 1` / `Floor 1_Black`, `AV_template_4` / `AV_template_4_white`.
8. **Логика и производные состояния — на клиенте.**
   - Redux-хранилище с ключами-строками вроде `[Media][Livingroom]Apple_TV`.
   - «Вентиляция включена» вычисляется в панели — в каждом клиенте заново.
9. **Посредник без модели.** iRidium Server объединял Crestron, CoolMaster, MQTT, Segnetics. Наружу — плоские теги, а не комнаты и устройства.
10. **Нельзя выключить функцию конфигурацией.** В меню телефона пункт так и называется: «Шторы(не работают)».

**Цена одного нового светильника:**
- SIMPL: модуль, сигналы, индексы joins;
- iRidium Server: тег;
- телефон: файл комнаты;
- планшет: страница комнаты и, может быть, план.

Это 4–5 мест в 3 инструментах, связанных только совпадением строк.

## Что было правильным

- Интерфейс генерировался из данных: плитки и списки, без нарисованных страниц.
- Единая точка входа для клиентов (iRidium Server).
- Хранилище состояния.
- Долгие операции с ожиданием, время которого приходит с сервера.
- Общие действия на уровне функции: «выключить весь свет», «закрыть все шторы».

## Главный вывод

Не хватало **архитектурной основы** — модели проекта, которая лежит под всеми слоями сразу.
Без неё каждый слой (логика, посредник, телефон, планшет) заводил свою копию дома, и они
расходились. Наш прототип повторил ту же ошибку: `HouseDef` описан кодом внутри клиента.
Основа описана в `12-foundation.md`.

## Медиа и климат в старом проекте (разбор скриптов iRidium)

**Медиа**
- **Сессиями медиа управлял отдельный сервер сценариев** (HTTP, порт 3000):
  - `/media?power=on|off|suspend&location=&source=` возвращает `ok|busy`, `timeout`, `current`;
  - `/query?location=`;
  - `/multiroom?op=enlist|exclude|start|stop|status`.
  - Идея верная: сессии держит сервер.
- **Политика при этом утекла в клиент:**
  - выбор источника («Apple TV 1 занят — пробуем Apple TV 2»);
  - передача источника между зонами «Кинотеатр» и «Гостиная» (ТВ → проектор без выключения источника);
  - блокировка «Проектор охлаждается».
  - Всё это написано в JS панели и повторено почти дословно для Apple TV и для Kodi.
- **Прогресс — это ожидание фиксированного времени** (`Modal_Timeout`), которое присылает сервер. Реальной готовности нет, потому что нет обратной связи.
- **Зависшие источники перезагружались из панели** через розетки PDU. Панель ходила к PDU и ресиверам Yamaha напрямую по публичному IP с пробросом портов, в обход ядра.
- **В гостиной две медиазоны** — «Кинотеатр» и «Гостиная» — с общим ресивером и громкостью. Медиазона ≠ комната.

**Климат**
- **Состояние одного контура разнесено по трём системам:**
  - уставка — Crestron;
  - включение и режим расписания — MQTT;
  - смена режима и загрузка недельного расписания — HTTP-сервер.
- **Расписания редактировались в панели** на каждый радиатор и пол отдельно и отправлялись JSON-ом.
- **Кондиционеры жили отдельно**, напрямую через CoolMaster: режим, уставка, питание.
- **Координации между полом, радиатором и кондиционером в клиенте нет.**
- **Жилец видел в комнате до трёх отдельных «термостатов».**

## Сервер сценариев (`vyborgskoe-node`, Node.js, ~1500 строк)

Express на порту 3000; два подключения CIP к контроллерам, MQTT, прямые HTTP-запросы к Yamaha.

**Что было верно**
- Источники и комнаты описаны данными: у источника — код входа матрицы или вход усилителя, у комнаты — список разрешённых источников.
- У источника есть владелец (`sources[x].in = комната`). Это по сути аренда: занято → `busy` с текстом «Устройство занято в комнате …».
- Исключение для пары «Кинотеатр ↔ Гостиная»: источник переходит без выключения.
- Мультирум как отдельный режим: стример (Yamaha 1 или 2) раздаётся на зоны усилителя; можно добавить или убрать зону.
- Сцены и расписания климата хранятся на сервере и редактируются из панели (`/setScen`, `/setFloors`, `/setHeaters`); есть движок расписаний «всегда / день / неделя».

**Что не масштабировалось**
- **Топология зашита в код.** Добавить комнату — значит поправить около 6 `switch` по имени комнаты в `powerOn`/`powerOff`. Joins матрицы и телевизоров лежат в объектах комнат: это четвёртая копия карты joins после SIMPL, iRidium Server и панели.
- **Нет плана перехода.** Время ожидания — сумма констант (`timeout += 100` для проектора), шаги — `setTimeout` «включить ТВ, через 5 с HDMI1» без проверки и отмены. Ошибки `fetch` не обрабатываются.
- **Блокировки неполные.** Охлаждение проектора проверяет клиент, а не сервер; при «занято» нет экрана блокировки с перехватом — клиент просто пробует второй экземпляр.
- **Состояние только в памяти.** После перезапуска сервер не знает, кто что смотрит.
- **Путаница экземпляра и вида:** `appletv2` превращается в `appletv` для MQTT-топиков, потому что интерфейс рисовал иконку по виду источника.
- **Ошибки:** в `setGlobalPower` цикл `for…in` по массиву перебирает индексы, а не имена, поэтому флаг «медиа выключено во всём доме» работал неправильно. В детской, кабинете и мастерской списки источников пустые — медиа там не управлялось.
- **Третья точка интеграции рядом с iRidium Server.** Состояние отдаётся ad hoc retained-топиками MQTT (`/media/livingroom/appletv/on`); у каждого клиента своя логика их сборки.
